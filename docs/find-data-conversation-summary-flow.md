# Find Data 左侧对话业务摘要与左右协同流程

- 文档版本：V1.0
- 更新日期：2026-09-05
- 状态：产品与交互规格，待实现与验收
- 适用范围：Find Data 执行页，先用于现有 Mock 场景的体验收口，后续 HTTP 模式沿用相同表达原则。

> 本文定义目标行为，不表示这些能力已经全部实现。本次仅新增文档，不修改业务代码、不改变生产服务模式，也不新增业务演示场景。

## 1. 问题与目标

### 1.1 当前问题

左侧对话的一些关键回复只有操作回执，例如：

> 正在按新口径重新评估；已更新候选资源、覆盖范围和关系证据。

这句话描述了系统动作，却没有回答用户真正关心的问题：

- 找到了哪些数据？
- 为什么推荐这些资源？
- 它们能支持当前目标的哪些部分？
- 当前还缺什么，有哪些限制？
- 我接下来可以做什么？

用户必须打开右侧面板才能理解结果，导致对话本身不完整。不同起步路径的完成反馈还不一致：有的显示资源概览和查看按钮，有的只有一句状态通知。

### 1.2 目标

关闭右侧面板时，用户仍然能理解当前任务的核心结论、推荐依据、重要限制和下一步。

右侧用于进一步核验、比较和操作，不应成为理解一句助手回答的前提。

改进重点是补齐信息，不是统一增加回复字数。普通问题仍可简短回答；检索完成、方案变化和分析完成等关键节点，应提供完整的业务摘要。

### 1.3 保留边界

- 保留 Task State / Reducer / Event，不建立第二套业务状态。
- 保留 Scenario Registry 和 Surface Policy，不在 React 组件中新增关键词路由。
- 保留 Mock / HTTP / Disconnected 分层，HTTP 回答不得回退为 Mock 结果。
- 保留 Candidate Pool 与 Data Solution 分离，以及替代资源单选约束。
- 保留权限单一真相、执行前重新鉴权、同一任务的操作顺序控制。
- 保留已确认的历史澄清决定，以及需求变化后的失效处理。
- 保留左侧对话、右侧工作区的整体布局，不把普通助手回答重新做成卡片。
- 找数完成不等于已经生成分析计划，更不等于分析已经执行。
- 不修改数据资产、业务对象、指标管理等无关页面。

## 2. 左右两侧的职责

| 信息 | 左侧对话：帮助理解和决策 | 右侧工作区：帮助核验和操作 |
| --- | --- | --- |
| 找数结果 | 核心资源名称、业务角色、覆盖概览、重要缺口 | 完整方案、逐项覆盖、证据、可执行范围 |
| 候选发现 | 本轮发现什么、为什么相关、是否已纳入方案 | 累计候选清单、筛选、选择状态 |
| 候选比较 | 推荐哪项、关键差异、选择代价 | 逐维度比较、字段入口、资源选择 |
| 字段问题 | 字段数量、代表性业务字段、与目标的关系 | 完整字段字典、分组、类型、搜索 |
| 权限问题 | 是否影响本次计算、哪些资源需申请、下一步 | 动作级权限矩阵、申请选择、申请记录 |
| 分析准备 | 本次要算什么、实际时间范围、待确认基准 | 公式、输入、基准依据、执行前校验与确认 |
| 分析结果 | 主要结论、关键数字、实际范围、结论边界 | 完整结果、计算依据和校验详情 |
| 修改需求 | 改了什么、保留或失效什么、如何继续 | 修改表单、重评中的方案、新版完整方案 |

允许适度重复：左侧说结论，右侧提供对应证据。两侧必须来自同一业务事实，不允许左侧说“已可执行”，右侧却显示该方案已失效。

## 3. 左侧回复的信息规则

### 3.1 关键节点采用五项检查，不强制五段模板

生成关键回复时，检查是否需要交代以下内容：

1. 结论：这一轮得到了什么，或为什么暂时得不到。
2. 概览：最重要的资源、变化或结果，避免只报一个数量。
3. 依据：为什么与用户目标匹配，为什么优先推荐。
4. 限制：尚未确认的时间、粒度、关系、权限或覆盖缺口。
5. 下一步：当前真正可用的操作，以及该操作会带来什么。

不相关的项目不必硬凑。禁止为满足模板编造推荐理由、缺口或结论。

### 3.2 按问题复杂度控制信息量

| 回复类型 | 表达要求 |
| --- | --- |
| 简单事实，如“它有多少字段” | 直接回答数量，必要时附查看入口；不重讲完整方案 |
| 局部解释，如“为什么选它” | 先回答选择理由，再补最相关的限制 |
| 阶段完成，如核心检索完成 | 使用短段落或短列表，完整交代结论、概览与下一步 |
| 方案变化 | 重点说本轮差异，不重复所有未变资源 |
| 执行完成 | 结果优先，明确数字、范围和边界，不用“请看右侧”代替答案 |
| 失败或受阻 | 说明本次没有完成什么、已有内容是否有效、可怎样恢复 |

首句应尽量给出业务结论。大规模候选或字段列表只呈现少量与目标最相关的条目，并明确“代表性条目”或“其余见详情”，不能把摘要伪装成完整清单。

### 3.3 措辞规则

- 不把“资源已更新、证据已重算、事件已完成”等工程过程作为唯一回复。
- 进行中使用“正在检索 / 正在重新评估”；成功后使用“已找到 / 已完成重新评估”。
- 不在完成回复中混用“正在”和“已完成”。
- 不使用内部资源 ID、场景键、权限枚举或原始证据标识代替业务说明。
- “发现候选”“加入方案”“纳入计算”“执行成功”必须严格区分。
- “当前没有已登记的缺口”不等于“数据完整且没有风险”。
- “可查询”不等于“可导出”，也不等于“已完成执行前鉴权”。
- “仅语义关联”不能改写为“已确认可以关联计算”。
- 不重复已展示的全文边界说明；但影响本轮判断的关键限制必须保留。

## 4. 回复与右侧面板的协调规则

### 4.1 基本流程

1. 用户提交问题或操作。
2. 既有意图解析与场景逻辑判断：普通问答、打开详情、变更任务，还是准备分析。
3. 普通问答读取当前有效状态；变更操作通过既有服务与事件流程处理。
4. 仅接受属于当前任务、当前操作的有效返回，并以本轮已生效事实生成回复。
5. 左侧先提供能独立理解的答案或完成摘要。
6. 右侧是否打开、替换或保持，由既有 Surface Policy 决定。
7. 需要用户进一步核验时，提供明确、可用的详情入口。

以上是职责与先后依赖，不要求通过人为延迟制造两次渲染。

### 4.2 不同输入的目标行为

| 用户输入或操作 | 左侧行为 | 右侧行为 |
| --- | --- | --- |
| “这个表有哪些字段” | 回答字段概览；目标不明则请用户选择资源 | 不因普通问题强制打开字段页 |
| “这两个资源有什么不同” | 给出关键差异及推荐理由，附比较入口 | 保持当前面板 |
| “比较这两张表” | 简短交代比较对象和结论 | 对象明确且允许时打开比较 |
| “打开完整字段列表” | 说明正在查看哪项资源；受阻则解释原因 | 目标与元数据权限满足时打开字段 |
| “我先看看民政相关资源” | 说明本轮新增、累计候选及尚未纳入状态 | 按既有策略打开相关资源 |
| “按当前方案分析” | 检查是否具备方案、是否缺少比较基准 | 不直接打开尚不存在的分析计划 |
| 点击“查看完整方案” | 不额外插入无信息量的“已打开”回复 | 展示当前有效方案 |
| 完成分析 | 直接给出关键结论和结果范围 | 在既有结果工作区展示并定位结果 |

### 4.3 操作入口

- 每轮通常突出一个主要下一步，其他操作弱化；不机械堆满按钮。
- 标签应说明对象和结果，例如“将月度快照加入方案”，避免“锁定选定资源入方案”。
- “继续分析”必须进入既有分析意图与场景判断流程，不能直接等价于打开或运行 Ask Plan。
- 只有已存在且有效的分析计划，才显示可用的“查看分析计划”。
- 普通问题目标不明确时，提供有限的、可发现的资源选项。选择查看目标不得隐式加入方案。
- 浏览切换不应产生重复业务总结；实际选择、变更、申请完成后才说明业务影响。
- 从比较进入字段后，应能返回比较并保留选择；返回上下文属于界面导航，不是新增业务方案状态。

## 5. 各阶段的业务流程

### 5.1 目标尚不明确

1. 简短复述已理解的目标。
2. 仅询问当前最影响检索的缺失条件。
3. 澄清选项说明业务区别，不要求用户先理解内部分类。
4. 用户明确提交后，才锁定决策并继续。

宽泛任务不能套用闵行默认资源。Generic 任务补充完整信息后，仍按既有允许条件进行场景升级；左侧可以轻量说明已理解的区域、时间与焦点，不显示场景键。

### 5.2 核心检索完成

成功回复至少说明：

- 核心资源是什么，以及分别承担什么作用。
- 时间、区域、粒度与需求的匹配情况。
- 目前能支持的分析方向，而不是宣称分析已经完成。
- 最影响使用的重要限制。
- 查看方案或继续补充数据的入口。

从宽泛目标澄清后检索、信息充分时直接检索，以及 Generic 补充后检索，都应获得同等完整的完成反馈，不能某条分支只有操作回执。

当仅发现部分匹配资源时，先说明“尚未形成完整核心方案”，再说明已发现资源能覆盖的部分。方案状态完成评估，不自动意味着具备可执行核心资源。

### 5.3 后续发现明细或相关候选

1. 说明本轮新增多少项；若面板展示累计候选，区分新增与累计。
2. 点出候选名称和各自适合的用途。
3. 根据当前时间范围和分析目标解释推荐顺序。
4. 明确“尚未自动纳入方案”。
5. 提供比较或选择入口。

候选数量、正式方案资源数量与核心资源数量分别计算；不能都写成“找到的方案资源”。

### 5.4 用户选择资源

操作成功后说明：

- 本轮加入或替换了哪项资源。
- 其角色是核心输入、条件支持、可选下钻还是部分匹配。
- 是否进入本次实际计算；没有进入时说明主要原因。
- 替代组中原资源是否退出正式选择。

未选中的替代候选可保留在 Candidate Pool，不应在回复中说它已经被删除。选择失败不显示“已加入”，并保留可恢复的选择状态。

### 5.5 查看资源与字段

已明确且允许查看的明细表：回答字段数量、代表性业务字段和与目标的关系，提供完整字段入口。

正式指标：优先解释指标定义、统计维度和来源，不把指标当作物理表，不能编造物理字段。

对象不明确：提供可发现资源的名称供用户选择，不只说“请先选择资源”而不给路径。

元数据不可访问：区分需申请、明确禁止、状态未知，不泄露不可发现资源的名称、字段或数量。

元数据未登记：说明“尚未登记”或“本演示未提供”，不得将其表达为真实业务表有 0 个字段，也不套用与资源无关的原因。

### 5.6 用户请求分析

1. 判断当前方案是否有效且满足准备分析的前置条件。
2. 没有核心资源或只有部分匹配时，在左侧解释为什么不能继续及可补充的方向。
3. 缺少比较基准时先澄清，并用一句话解释选项的业务含义。
4. 基准确认并实际准备好计划后，左侧总结本次计算内容、实际分析范围、比较基准和下一步。
5. 用户明确查看计划后，在右侧核验公式、输入和权限。
6. 执行仍需明确确认，并保留执行时重新鉴权。

这里的“可继续分析”不代表无需权限校验，也不能仅根据所有资源当前可查询就承诺计算一定成功。

### 5.7 权限快照、申请与重检

左侧优先回答权限对本次任务的影响，而不是逐项朗读权限矩阵：

- 核心资源当前都可查询：说明本次核心计算无需额外申请，但执行前还会校验。
- 可选候选需申请：明确不一定影响当前核心计算。
- 核心权限受阻或发生变化：点出受影响的可发现资源、影响以及允许的恢复路径。
- 申请提交成功：说明申请对象、动作、申请编号和已提交状态；不能说权限已经获得。
- 没有核心资源：解释方案尚未具备核心资源，不显示“核心权限全部通过”。

右侧继续负责逐动作权限与申请记录。左侧不能绕过原有申请范围、动作级校验、重复申请和原子校验规则。

### 5.8 分析完成

左侧至少呈现：

1. 服务实际返回的主要结论。
2. 关键数字、对象及比较基准。
3. 本次实际分析的时间与范围。
4. 演示/真实结果来源以及关键结论边界。
5. 查看完整结果或计算依据的入口。

右侧应直接定位结果，不要求用户先滚过整份计划。普通回答不能只说“分析完成，详情见右侧”。

必须区分资源覆盖范围、计划请求范围和实际执行范围。例如资源覆盖过去 12 个月，但 Mock 只返回最新月演示，则分析前应明确限制，结果也应重复标明实际月份。

如果当前返回协议没有足够信息证明实际执行范围，必须说明范围尚未确认，并将补齐范围元数据列为后续实现依赖。不能从资源覆盖、任务标题或当前日期推断实际计算月份。

分析数量和统计结论以服务返回为准。服务返回的两条展示记录不必然代表全区只有两个低值街镇；缺少权威总数时只陈述已返回记录，不自行推导整体数量。

### 5.9 修改需求与重新评估

1. 用户保存前，说明将重新评估方案，已有分析结果可能不再适用于新需求。
2. 需求保存后，沿用原有失效与重新检索事件流程。
3. 进行中只显示真实进度；旧内容如用于过渡，明确为历史/待重评，不继续推荐执行。
4. 成功后说明新范围、本轮保留/新增/移除的关键资源，以及旧计划或结果是否失效。
5. 未配置区域或时间不满足时，说明当前缺口，并给出调整条件等用户可执行的下一步。
6. 失败时说明新方案尚未形成，提供重试入口，不把旧方案恢复成新需求下的有效方案。

沿用既有关键事件次序：

1. `REQUIREMENT_UPDATED`
2. `ASK_PLAN_INVALIDATED`
3. `COMPARISON_MODEL_CLEARED`
4. `SOLUTION_EVALUATION_STARTED`
5. `SEARCH_STARTED`
6. `SEARCH_RESULTS_RECEIVED`
7. `ASSISTANT_TURN_RECEIVED`

发生场景变化时，仍按既有场景逻辑产生重分类事件。本文不重新定义完整事件协议。

最终回复重点是可理解的变化，不要求展示内部 Revision 数字。

### 5.10 提交失败与恢复

- 一次变更操作只产生一次有效完成反馈，旧操作返回不能插入新的成功摘要。
- 澄清失败后保留用户选择并允许重试，不能永久停在“提交中”或提前标为已确认。
- 权限申请失败不能显示已提交；分析失败不能生成成功结论或虚构数字。
- 重试后成功，以有效操作结果为准，避免重复添加同一资源、申请或回复。
- Disconnected 模式说明能力尚未连接，不生成看似成功的资源或分析摘要。

## 6. 文案示例

以下仅用于说明表达方式。资源名称、数量、日期、权限和数字必须由本轮状态或服务结果提供，不得将这些例句写成所有场景共用的固定结果。

### 6.1 核心检索完成

> 围绕闵行区过去 12 个月的养老床位供给，目前找到了两项核心指标：60 岁以上常住人口数和在营可用养老床位数。
>
> 前者提供老年人口基数，后者提供实际可用床位规模，两项资源的时间覆盖能够满足本次找数范围。后续可以用它们计算各街镇每千名老人拥有多少养老床位。
>
> 两项指标都按街镇和月份组织，但具体维度与时间对齐仍需在分析阶段验证。你可以先查看完整方案；如果需要人口明细，我也可以继续找。

操作示例：查看完整方案 / 寻找人口明细。需要展示“继续分析”时，必须按第 5.6 节进入分析前置判断。

### 6.2 人口明细候选发现

> 本轮新增了两项人口明细候选：人口基本信息视图和常住人口月度快照，目前都还没有加入方案。
>
> 对于过去 12 个月的目标，月度快照更适合：它保留历史月份，可以按月查看人口明细；基本信息视图只保留当前状态，而且查询需要申请权限。
>

## 7. 历史、当前状态与一致性

### 7.1 历史消息不是新的业务真相

- 历史回复保留其生成时的业务内容，不能用新任务状态悄悄改写旧结论。
- 展示时可以根据需求、检索和计划版本增加“历史方案 / 已被新需求替代 / 结果已失效”等标记。
- 历史澄清决定保持只读，失效由任务状态决定，不依赖组件永久本地状态。
- 历史“查看当前方案”若实际跳转到最新方案，应明确指向“最新方案”；不得让用户以为仍在查看当时的两项资源。
- 失效的执行操作必须不可用，并提供原因或前往当前有效方案的入口。

### 7.2 摘要与详细数据保持一致

- 资源概览、数量、角色与覆盖来自本轮有效 Task 与对应搜索结果。
- 权限摘要来自资源上的动作级权限，执行结论来自本次有效执行结果。
- 所有重要数量区分检索总匹配数、实际返回数、累计候选数、方案项数与执行输入数。
- 缺少证据时表达未知，不把字段存在推导成数据质量已通过，不把可发现推导成可查询。
- 关闭或打开右侧面板不会改变资源选择、权限、方案或分析结果。

1. 优先使用既有 `TEXT`、`ACTION_GROUP`、`CLARIFICATION`、`RUNTIME_STATUS` 和 `SYSTEM_NOTICE` 等 Block。已有 `RESULT_BRIEF` 可以服务于确实需要的结果概览，但不能把所有回答升级为卡片。
2. 业务摘要基于操作生效后的状态生成。服务侧需要先应用领域事件得到本轮快照，再组织成功回复；不能拿操作前的方案写出新结果。
3. 沿用 `ASSISTANT_TURN_RECEIVED` 的会话写入路径。服务结果中的 `events` 与 `assistantBlocks` 不能被重复追加成两条相同回复。

5. 新增历史来源标记或实际执行范围元数据时，仅补充必要、可验证的关联信息；不另造独立业务状态机。没有这些事实前，不以模板猜测补全。
6. Mock 文案由 Mock 的有效状态生成；HTTP 文案使用后端真实事实或返回内容；Disconnected 明确不可用。不能用前端固定示例伪装通用智能回答。
7. 内部证据引用只有在能映射为业务可读、允许展示的说明时才进入回复；不直接输出内部 ID 列表。

## 9. 展示与可访问性要求

- 普通回答以自然段为主，必要时使用短列表或紧凑对比表，避免多层嵌套面板。
- 核心结论和关键数字优先；完整字典、长权限矩阵和长证据放右侧。
- 左侧最新阶段摘要应容易找到，不要求用户滚回很早的消息寻找唯一入口。
- 已确认的澄清可以收为简短只读摘要，但保留查看历史决定的方式。
- 单选和多选应有正确语义、标签和选中反馈，不能只靠颜色。
- 按钮需要可辨识名称，禁用操作有原因；加载完成与失败反馈应能被辅助技术感知。
- 加长回复不能造成输入框不可见或长文本横向溢出；窄窗口下仍可读。
- 初次演示及分析结果明确标识演示环境/演示数据，不向业务用户显示内部枚举。

## 10. 验收标准

验收重点是业务信息是否充分且真实，不以字符数、段落数或卡片数量作为通过条件。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 关闭右侧完成首次找数 | 左侧可独立理解核心资源、用途、覆盖、限制和下一步 |
| AC-02 | 宽泛目标、直接目标、Generic 补充三条路径 | 同等阶段拥有完整成功摘要，不存在只输出状态回执的分支 |
| AC-03 | 搜索进行中与完成 | 两种措辞明确分离，完成后不继续显示“正在重新评估”作为最终回复 |
| AC-04 | 用户只问字段数量 | 直接回答，不重讲整套方案，也不强制打开右侧 |
| AC-05 | 用户问字段但对象不明 | 提供可发现资源的选择路径，且选择查看目标不隐式加入方案 |
| AC-06 | 指标、未登记元数据、权限受阻 | 分别解释，不虚构物理字段，不泄露不可发现资源 |
| AC-07 | 人口明细检索完成 | 左侧列出候选及推荐理由，明确尚未纳入；方案不自动新增两项明细 |
| AC-08 | 本轮新增与累计候选不同 | 左侧与右侧明确两个数量的含义 |
| AC-09 | 用户选择月度快照 | 说明已加入及其下钻角色，不宣称已进入核心计算 |
| AC-10 | 询问两资源差异 / 明确要求比较 | 前者先摘要并保持面板，后者按策略打开明确比较对象 |
| AC-11 | 请求分析但缺基准 | 先澄清，不打开不存在的计划，不自动执行 |
| AC-12 | 请求分析但无核心方案 | 左侧说明缺失条件及恢复方向，不显示“全部校验通过” |
| AC-13 | 候选需要权限而核心已允许 | 明确候选申请不一定影响本次核心计算 |
| AC-14 | 权限申请提交成功 | 说明申请对象、动作、编号和提交状态，不把权限写为已获得 |
| AC-15 | 分析完成 | 不开右侧也能获得主要结论、关键数字、实际范围和边界 |
| AC-16 | 12 个月目标但仅最新月演示 | 分析前明确本次限制，结果明确实际月份，不声称做过全年分析 |
| AC-17 | 执行结果缺少范围或统计总数 | 明确未知或仅描述返回记录，不从日期/展示行数推断完整结论 |
| AC-18 | 点击查看完整结果 | 右侧定位结果，不仍停在计划顶部 |
| AC-19 | 修改需求完成重评 | 说明关键变化和旧计划失效，历史内容有清晰版本语义 |
| AC-20 | 修改为未配置区域 / 时间不覆盖 | 不继续推荐旧方案，提供真实缺口和可执行的调整路径 |
| AC-21 | 澄清、搜索、选择或分析失败 | 不出现成功摘要，保留允许重试的状态并解释影响 |
| AC-22 | 重复请求、旧操作返回或任务切换 | 无重复回复、无过期摘要写入当前任务 |
| AC-23 | 两侧事实一致 | 名称、数量、角色、覆盖、权限和结果均来自对应有效事实 |
| AC-24 | HTTP / Disconnected | 不使用 Mock 文案和数字填补失败或未知事实 |
| AC-25 | 键盘、辅助技术、窄窗口 | 选择与操作有正确名称和状态，回复和下一步可读可达 |

建议测试层次：Presenter 单元测试覆盖事实表达；Service/Reducer 测试覆盖事件、版本与顺序；组件及浏览器测试覆盖不打开侧栏也可理解、面板策略、失败重试和结果定位。

## 11. 建议实施顺序与完成定义

### 第一阶段：补齐关键摘要

- 统一首次检索成功反馈。
- 完善候选发现、选择与字段概览。
- 完善分析结果摘要，并提前披露实际执行范围限制。
- 不变更普通问答的 Surface Policy。

### 第二阶段：补齐变化与恢复

- 需求重评差异摘要、历史版本标记。
- 权限对本次任务影响的解释。
- 失败重试与过期结果不插入对话。

### 第三阶段：交互一致性

- 统一详情入口与返回上下文。
- 结果定位、历史澄清收纳、文字可读性与无障碍检查。

后续实现完成时，应提交代码与相应测试，运行仓库要求的检查，并按上述验收路径提供证据。本次文档交付不代表这些实现检查已经执行。

最终判断标准：用户不打开右侧，也能回答“现在找到了什么、为什么选它、还缺什么、这次实际算了什么、我下一步能做什么”。
